# ARCH-001 — RethinkDNS Architecture

**Document ID:** ARCH-001  
**Version:** 1.1  
**Status:** Published  
**Last Updated:** 2026-09-01  
**Project:** Android OPSEC Hardening  
**Scope:** Android network security and privacy architecture  
**Reference Device:** Samsung Galaxy A50 (SM-A505G)

---

## 1. Purpose

This document defines the reference architecture for integrating RethinkDNS into the Android OPSEC Hardening project.

The objective is to describe how RethinkDNS interacts with Android, application isolation, DNS filtering, VPN tunnels, firewall policies, and application-specific network routing.

This document describes an architectural reference rather than a universal configuration.

Individual deployments may require different settings depending on:

* Device hardware.
* Android version.
* ROM implementation.
* Kernel capabilities.
* Network environment.
* VPN provider.
* DNS provider.
* Application requirements.
* Privacy requirements.
* Security objectives.
* Performance and battery constraints.

The architecture should therefore be adapted and validated according to the requirements of each deployment.

---

# 2. Architectural Objectives

The reference architecture is designed around the following objectives:

1. Provide centralized network control on Android.
2. Apply DNS-based filtering and policy enforcement.
3. Route selected applications through dedicated VPN tunnels.
4. Support application-level network segmentation.
5. Provide firewall-based traffic control.
6. Reduce unnecessary network exposure.
7. Provide visibility into DNS and network activity.
8. Support isolated application environments.
9. Allow individual security layers to be tested independently.
10. Maintain a reproducible baseline for future changes and software updates.

The architecture prioritizes **defense in depth** rather than relying on a single security mechanism.

Each component has a defined role and should not be considered a complete replacement for the other layers.

# 4. Architectural Components

## 4.1 Android / Compatible ROM

Android provides the operating-system environment in which the architecture is deployed.

The original reference implementation used crDroid, while the architecture itself is not dependent on a specific ROM.

The operating system provides the underlying mechanisms required for:

* Application execution.
* Network connectivity.
* User and profile isolation.
* VPN interfaces.
* Application permissions.
* System networking.
* Network state transitions.

The behavior of these mechanisms may vary between Android versions and ROM implementations.

---

## 4.2 Shelter

Shelter provides application isolation through Android's managed work profile functionality.

In the reference deployment, application isolation is used to establish separate trust contexts.

A work profile can be used for applications that require additional isolation from the primary environment, including:

* Testing applications.
* Applications with uncertain network behavior.
* Applications requiring separate VPN routing.
* Applications that should not share the same operational environment as personal applications.

Shelter provides **application and profile isolation**.

It should not be considered a network security boundary by itself.

Network traffic generated by applications inside the profile remains subject to the Android networking stack and the network controls configured on the device.

---

## 4.3 RethinkDNS

RethinkDNS acts as the central network control layer of the reference architecture.

Depending on the configuration, it can provide:

* DNS configuration.
* DNS filtering.
* Firewall controls.
* Application-level network policies.
* Proxy routing.
* WireGuard integration.
* Application-specific traffic routing.
* Network logging and observability.
* Network automation.

RethinkDNS therefore occupies a central position between applications and the external network.

Its role is not limited to DNS resolution.

---

## 4.4 Encrypted DNS Provider

The DNS provider supplies the upstream DNS resolution and, depending on the selected service, may also provide filtering and policy enforcement.

Possible capabilities include:

- DNS resolution.
- Domain filtering.
- Security blocklists.
- Privacy-oriented filtering.
- Custom deny/allow rules.
- Query logging.
- Policy-based classification.

Providers used or evaluated within the project include:

- NextDNS.
- modDNS.

The architecture does not require a specific DNS provider.

RethinkDNS remains the local network-control layer while the selected resolver provides the upstream DNS service.

Possible encrypted transports include:

- DNS over HTTPS (DoH).
- DNS over TLS (DoT).

DNS behavior must be validated according to the intended deployment, because resolver selection may interact with proxy configuration, WireGuard routing, Split DNS, network state, and software version.

---

## 4.5 WireGuard

WireGuard provides encrypted network tunnels used for selected network flows.

The reference implementation supports multiple WireGuard configurations for different application-routing requirements.

For example:

```
Application Group A
        |
        v
    WireGuard 01
        |
        v
    VPN Endpoint A


Application Group B
        |
        v
    WireGuard 02
        |
        v
    VPN Endpoint B
```

This model allows applications or application groups to use different network paths when required.

Multiple tunnels increase flexibility but also increase configuration complexity.

---

## 4.6 VPN Provider

The VPN provider supplies remote endpoints used by WireGuard configurations.

RethinkDNS is responsible for applying the configured application-level routing policy, while WireGuard provides the encrypted tunnel transport.

The architecture is VPN-provider independent.

Providers used or evaluated by the broader project include:

- Proton VPN.
- Mullvad.
- IVPN.

Provider selection should consider the deployment requirements, WireGuard compatibility, privacy characteristics, operational reliability, and available configuration options.

Provider reputation alone does not validate the local routing architecture.

The resulting traffic path should be independently verified.

# 6. Application Segmentation

One of the main architectural capabilities provided by the combination of Android profiles and RethinkDNS is application-level segmentation.

The reference architecture can use different network policies for different applications.

For example:

```
                         RethinkDNS
                             |
              +--------------+--------------+
              |              |              |
              v              v              v
          Personal        Work          Testing
              |              |              |
              v              v              v
          Direct /       VPN/WG        VPN/WG/TOR
          selected       selected       selected
```

The important architectural distinction is that different mechanisms provide different forms of isolation.

| Mechanism | Primary purpose |
|---|---|
| Android / ROM | Operating-system environment |
| Work profile / Shelter | Application/profile isolation |
| RethinkDNS | Network policy and traffic control |
| Firewall | Traffic restriction |
| Encrypted DNS provider | DNS resolution and optional filtering |
| WireGuard | Encrypted network transport |
| VPN provider | Remote network endpoint |

Application isolation and network isolation should therefore not be treated as equivalent mechanisms.

---

# 7. Trust Model

The reference architecture uses different trust levels to determine where additional controls may be appropriate.

A simplified model is:

```
                    HIGHER TRUST
                         ^
                         |
                  Personal Apps
                         |
                  ----------------
                         |
                    Work Profile
                         |
                  ----------------
                         |
               Testing / Unknown
                         |
                         v
                    LOWER TRUST
```

The trust level does not indicate that an application is malicious.

It represents the level of confidence assigned to the application within the deployment.

Applications with lower trust may therefore receive additional controls such as:

* Dedicated VPN routing.
* Additional DNS filtering.
* Application-specific firewall rules.
* Profile isolation.
* Separate testing environments.

This model allows security controls to be proportional to the perceived risk instead of applying the same configuration to every application.

---

# 8. Defense in Depth

The architecture does not treat DNS filtering, VPN encryption, application isolation, or firewall controls as interchangeable mechanisms.

Each layer addresses a different security objective.

| Layer | Component | Primary Function |
|---|---|---|
| Operating System | Android / compatible ROM | Platform and application controls |
| Isolation | Work profile / Shelter | Application/profile separation |
| Network Control | RethinkDNS | Firewall, proxy and routing |
| DNS Policy | Encrypted DNS provider | DNS resolution and optional filtering |
| Transport | WireGuard | Encrypted network tunnel |
| VPN Provider | Compatible VPN provider | Remote network endpoint |
| Observability | RethinkDNS / DNS provider | Network and DNS visibility |

The resulting model is:

```
                 APPLICATION
                      |
                      v
              +---------------+
              | Work Profile  |
              |  (optional)   |
              +-------+-------+
                      |
                      v
              +---------------+
              |  RethinkDNS   |
              +-------+-------+
                      |
          +-----------+-----------+
          |           |           |
          v           v           v
         DNS       Firewall     Proxy
          |                       |
          v                       v
     Encrypted DNS            WireGuard
       Provider                   |
                                  v
                             VPN Provider
                                  |
                                  v
                               Network
```

The architecture should be evaluated as a complete system while retaining the ability to test individual layers independently.

# 9. DNS Architecture

DNS is treated as an independent security and privacy layer within the architecture.

The logical relationship is:

```
Application
    |
    v
RethinkDNS
    |
    v
DNS Policy
    |
    v
Encrypted DNS Provider
    |
    v
DNS Infrastructure
```

Possible upstream providers include NextDNS, modDNS, or another compatible encrypted resolver.

The DNS provider is intentionally abstracted from the RethinkDNS network-control layer.

The actual DNS path may change depending on:

- RethinkDNS configuration.
- Split DNS configuration.
- Proxy configuration.
- WireGuard configuration.
- DNS bypass rules.
- Application-specific routing.
- DNS transport.
- Android network state.
- Software version.

For this reason, the architecture does not assume that every DNS query will necessarily follow the same path.

DNS behavior must be validated against the intended deployment.

---

# 10. Multi-Proxy Architecture

The reference deployment makes use of RethinkDNS's ability to associate different proxy configurations with specific applications or application groups.

A simplified model is:

```
                     RethinkDNS
                         |
          +--------------+--------------+
          |              |              |
          v              v              v
       General       Application A   Browser
          |              |              |
          v              v              v
       WG-General    WG-Specific       TOR
          |              |              |
          v              v              v
      VPN Exit A     VPN Exit B     TOR Network
```

This provides a form of application-aware network segmentation.

The purpose is not to maximize the number of VPN tunnels.

Additional tunnels should only be introduced when they provide a clear operational or security benefit.

Potential benefits include:

* Application-specific exit locations.
* Separation of traffic classes.
* Different routing policies.
* Dedicated testing paths.

Potential drawbacks include:

* Greater configuration complexity.
* Increased troubleshooting requirements.
* More potential failure points.
* More difficult traffic-flow analysis.

---

# 11. Firewall Architecture

RethinkDNS provides the firewall enforcement layer.

The firewall can be used to restrict traffic based on application and network policy.

Examples of controls evaluated in the reference deployment include:

* Blocking applications when the device is locked.
* Blocking insecure HTTP traffic on port 80.
* Restricting application connectivity.
* Controlling traffic according to proxy and routing policies.

Firewall settings should be evaluated according to the application requirements.

A restrictive rule that improves security in one environment may cause unacceptable functionality problems in another.

Therefore, firewall policies should be validated before being considered part of a stable configuration.

---

# 12. Observability

Observability is an important component of the architecture.

Security controls should not operate as opaque mechanisms.

The reference architecture may use:

- RethinkDNS network logs.
- RethinkDNS connection information.
- DNS-provider logs when available.
- VPN connection state.
- Application-level observations.
- External validation tools.
- Packet-level captures when required by the validation objective.

The objective is to correlate:

```
Application
     |
     v
RethinkDNS
     |
     +---- DNS query ----> Encrypted DNS Provider
     |
     +---- Proxy --------> WireGuard
     |
     +---- Firewall -----> Allow / Block
     |
     v
External Network
```

This allows unexpected behavior to be investigated rather than simply assumed to be a configuration error.

---

# 13. Version Dependency

The architecture is dependent on software behavior.

RethinkDNS networking behavior may change between releases.

The project therefore distinguishes between:

```
Architectural Reference
        |
        +---- Historical Baseline
        |
        +---- Current Validation Environment
        |
        +---- Candidate Version
```

The original architecture was established using RethinkDNS v0.5.5x.

Subsequent validation has included RethinkDNS v0.5.6.

The authoritative software version for a specific result is the version recorded in the corresponding validation report.

A new release should not automatically replace an established baseline.

Instead:

```
                 Known Baseline
		      |
		      v
		Configuration Backup
		      |
		      v
		Candidate Version
		      |
		      v
		Validation
		      |
		 +----+----+
		 |         |
		PASS      FAIL
		 |         |
		 v         v
		Accept   Investigate /
			 Roll Back
```

Version-specific behavior should be documented through validation reports or Engineering Notes when appropriate.

# 14. Design Trade-offs

The reference architecture intentionally introduces additional complexity in exchange for greater control.

## Potential benefits

* Application-level network control.
* DNS policy enforcement.
* Application-specific VPN routing.
* Multiple network paths.
* Application/profile segmentation.
* Firewall enforcement.
* Network observability.
* Greater flexibility for testing.

## Potential costs

* Increased configuration complexity.
* Greater troubleshooting requirements.
* Additional VPN and DNS dependencies.
* Possible compatibility issues.
* Version-specific behavior.
* Potential performance impact.
* Potential battery impact depending on configuration.
* Greater difficulty reproducing the configuration on different devices.

A simpler configuration may therefore be preferable for users whose security and privacy requirements do not justify the additional complexity.

The objective is not to maximize the number of security controls.

The objective is to apply appropriate controls according to the threat model and operational requirements.

---

# 15. Security Boundaries and Limitations

This architecture does not guarantee complete anonymity, complete protection against malicious applications, or protection against every possible Android or network-level threat.

The effectiveness of each layer depends on:

* Correct configuration.
* Android behavior.
* ROM implementation.
* Application behavior.
* VPN provider behavior.
* DNS provider behavior.
* Network conditions.
* Software versions.
* IPv4/IPv6 configuration.
* Device capabilities.

In particular, DNS filtering should not be considered a substitute for application isolation, VPN encryption, endpoint security, or operating-system security controls.

Likewise, a VPN should not be considered a substitute for DNS filtering or application-level security policies.

The architecture should therefore be evaluated as a defense-in-depth system.

# 16. Adaptability

The reference architecture is intentionally modular.

Components may be replaced or removed according to deployment requirements.

For example:

```
                    RethinkDNS
                        |
          +-------------+-------------+
          |             |             |
          v             v             v
         DNS         Firewall       Proxy
          |                           |
          v                           v
   Encrypted DNS                  WireGuard /
      Provider               Compatible Transport
                                  |
                                  v
                             VPN Provider
```

Possible variations include:

* Different DNS providers.
* Different VPN providers.
* Different WireGuard endpoints.
* Different Android ROMs.
* Different application isolation strategies.
* Different firewall policies.
* Different DNS transports.

Any change should be validated against the intended security objective.

# 18. Validation Requirements

Before considering a deployment based on this architecture stable, the following areas should be validated:

* DNS resolution.
* DNS filtering.
* DNS routing.
* VPN connectivity.
* Application-specific proxy routing.
* Firewall behavior.
* IPv4 behavior.
* IPv6 behavior when enabled.
* Network transitions.
* Wi-Fi behavior.
* Mobile-data behavior where applicable.
* Device restart behavior.
* Application startup behavior.
* RethinkDNS restart/recovery behavior.
* DNS and network logging.
* Expected behavior after configuration changes.

Validation procedures will be documented separately.

This document defines the architecture; it does not constitute the complete validation procedure.

Validation coverage may be distributed across multiple validation reports.

A deployment should not be described as universally validated when only a subset of these areas has been tested.

## Architectural Principle

> **Security controls should be understandable, testable, and proportional to the threat model they are intended to address.**

Android OPSEC Hardening does not aim to provide a single "perfect" configuration.

It aims to provide a reproducible framework for designing, testing, documenting, and maintaining Android security and privacy architectures.
